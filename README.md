V4 相较 V3 补的两块（都是 CS 闭环里原本会漏的一环）：
- **「再来一单」（S-12）**：订单详情按**当前货架**补货 —— 数量不照抄历史订单，
  缺货/下架的点名告知；顺序上先换栋再补货（购物车绑楼栋，反过来会自己清空自己）。
- **消息兜底（CS-13）**：每次状态流转落一条**站内消息**。微信订阅消息有三条绕不过的限制
  （一次授权只发一条 / 学生可永久拒收 / 未认证无模板资格），所以推送只做增强，站内消息才是主通道。
  授权结果原样入库，且在发送通道未就绪时**不消耗**一次性授权。

V5 补的是「商户能干活」这半边（10 页小程序 + 11 页网页），其中三条是设计纪律而不是功能清单：

- **配送清单里没有时间序**（AC-03 硬要求）：楼栋 → 楼层 → 房间号 的空间序由服务端排好，
  前端只做分桶不做重排，界面上不存在"按时间排序 / 由新到旧"的切换 —— 商户在楼里送一趟，
  要的是"这栋还有哪些房间"，不是"谁先下单"。
- **送达的"撤销"是延迟提交，不是回滚**：`delivered` 是终态，提交后改不回来。所以勾选后
  先本地标记 + 5 秒后才真正发请求，撤销 = 撤掉这次提交。若做成"提交完再给撤销按钮"，
  那个按钮点了必然报错 —— 那是在骗人。
- **库存快改与盘点调整是两个接口**：手机端快改是高频小幅可逆动作，理由由服务端固定；
  网页端 `adjust` 理由必填。共用一个接口 + "理由可缺省"开关，等于把"库存对不上时
  查不出谁改的"这个可追溯性换掉，只为省一个弹窗。
- **两个"同步"在界面上就是两个按钮**（AC-10）：同步上架只改上下架、同步库存只改数值，
  各自在弹窗里写明"不会动另一件"。合成一个"同步"，就会发生"我只是补货，结果某栋被上架了"。
- **后台登录码闭环**：网页端不另设密码，由店主在小程序「我的 → 网页后台登录码」生成
  6 位码（5 分钟 · 一次性 · 按租户限流），网页端拿码换 24 小时店主令牌。
  签发登录码 ≈ 签发店主令牌，所以该接口与学生令牌之间是**默认拒绝**（403，不是 401 ——
  他有身份，只是不是店主；混用会让前端把"你没权限"提示成"请重新登录"）。

S2 的两半：**钱**（`src/ledger/`）与**货**（`src/catalog/`）。两者平行、互不依赖 ——
订单域将来会同时用它们，但货和钱之间不该有依赖，否则会出现"改库存要注入账本"这种荒唐依赖。

V6 是「我方怎么管这盘生意」这半边（平台后台 13 页 + 上线流水线）。这一期的核心判断是：

**§5 那三个非代码瓶颈（审核会驳回 / 商户号必须本人办 / 密钥与版本运维）不该被当成"沟通问题"
放在微信群里，而应该做成有状态、有时长、有责任人的对象。** 所以：

- **驳回是一等状态，不是错误**：流水线阶段有 `rejected`（琥珀色，不是红色），
  驳回后进**返工队列**并开始计时。把驳回当异常处理，结果就是"驳回了但没人知道，
  等想起来时已经过了半个月" —— 而驳回恰恰是这个行业最常发生的事。
- **每个阶段都记「卡了几天 + 上次触达」**，且**由服务端算好下发**。
  理由不是洁癖：卡天数若用浏览器时间算，操作员把系统时间往回调就能让看板全绿 ——
  而"看板全绿"正是没人在管最危险的信号。**外部阶段（备案 / 商户号）卡住不算我方超期，
  但照样要显示**，因为它仍然是这笔生意的真实瓶颈。
- **密钥只可替换、不可查看，且这不是权限设置而是数据结构**：表里只有密文，
  接口层只回掩码，**没有任何一个接口能返回明文**（冒烟里有一条断言逐接口验证这件事）。
  有人日后"顺手加一个查看按钮"是加不出来的 —— 服务端手上就没有。
  失效标记不做成删除：删掉后那一格会消失，又掉回"以为齐了"的坑。
- **灰度推送的闸门做在服务端**：灰度上限 2 家、"灰度未过不许批量"这两条若只写在界面上，
  第一个想走捷径的人用 curl 就绕过去了。发布通道 `DeployProvider` 是抽象出来的，
  现在挂 mock（本地 20 个伪 AppID 全跑通），接真 `miniprogram-ci` 时只换这一个实现。
- **平台侧的中性色是两层护栏**（AC-12）：`lockNeutral()` 从 CSS 变量层堵
  （`.p-shell` 内 `--brand-*` 一律解析成墨色，共用类照用也不会变色），
  `check-platform-neutral.mjs` 从源码层扫。**两层都要有** —— 变量层挡「顺手写错」，
  源码层挡「有人在别处新造一个品牌色变量」。只写文档约束的是记得它的人。
- **对账只报不自动扣**：`diffCents ≠ 0` 时生成差异行 + 进告警，**不自动补扣**。
  自动补扣在没有 RBAC 和操作审计的过渡期，等于把"钱可以对不上"这件事静默化。

## 运行

```bash
npm install

# ---- 服务端 ----
npm run build:server    # 必须先编 tokens 再编 server
npm run smoke           # 真实起服务 + 真实打 HTTP + 175 项断言（54 个分组）
npm run dev:server      # 开发模式（node --watch），默认 3000 端口
npm run start:server    # 直接起编译产物
```

### 微信小程序凭据：填在哪、怎么验证、什么时候必须重置

凭据只有**三处**，多一处都是隐患：

| 位置 | 放什么 | 能不能入库 |
|---|---|---|
| `apps/mini/src/manifest.json` → 顶层 `appid` **和** `mp-weixin.appid` | AppID | ✅ 可入库（非机密） |
| `apps/server/.env.local`（本机）/ 生产 `.env` | `WECHAT_APPID` + `WECHAT_APPSECRET` | ❌ 绝不入库 |
| 公众平台「开发 → 开发管理 → 服务器域名」 | 后端 https 域名 | 平台侧配置 |

> ⚠️ 只改 `manifest.json` 顶层的 `appid` **不够** —— 产物的 `project.config.json`
> 会停留在 `touristappid`，开发者工具里表现为"登录拿不到 openid"。
> 两处必须同时填。

**配好了没有？让服务自己回答**，不要靠猜：

```bash
curl -s http://127.0.0.1:3000/api/tenant/auth/status | cat
```

- `wechat.configured: true` + `hint` 带 AppID 尾号 → 已就绪；
- `false` + `hint` 指出缺哪个环境变量 → 还没配，而且它会告诉你是哪一个；
- 学生登录返回 `WECHAT_NOT_CONFIGURED` → 同一件事的另一种问法，
  刻意与"网络错误""code 失效"分开，免得排障时查错方向。

**真机预览的硬门槛**（不是本项目能绕过的）：真机走真实域名校验，
所以后端必须是 **https + 已备案域名**且已加入 request 合法域名；
纯 IP + 端口在真机上永远不通。开发者工具里勾「不校验合法域名」只对模拟器与
真机调试模式有效，那是为了开发期能连本机，不是为了绕开这条规定。

**什么时候必须重置 AppSecret**：它出现在这份清单之外的任何地方
（聊天记录、截图、issue、日志、发给别人的 `.env`）就等于已泄露。
处置只有一步：公众平台 → 开发设置 → **重置**，然后把新值写进上面那一处。
这也是它只允许存在一个位置的原因 —— 位置多了，重置时必然漏改。

### 开发者工具里连不上后端？

```
POST http://127.0.0.1:3000/api/tenant/resolve net::ERR_CONNECTION_REFUSED
```

这是**网络层拒绝**，不是接口错。按顺序查两件事：

1. **服务端起了吗** —— `ERR_CONNECTION_REFUSED` 只有一个意思：3000 端口没人监听。
   在另一个终端跑 `npm run dev:server`。开发者工具里的请求由工具进程发出，
   所以 `127.0.0.1` 指的就是你这台电脑，**不需要**局域网 IP、也不需要 https。
2. **连上了但显示「店铺未开通」** —— 服务端起来了，但这个 AppID 在内存库里没有对应租户。
   跑 `npm run seed:dev`（它会读 `apps/server/.env.local` 里的 `WECHAT_APPID`）。

真机预览 / 体验版 / 正式版另说：**必须是 https + 已备案域名**，IP + 端口在真机上一定不通
（把 `apps/mini/.env.local` 的 `VITE_API_BASE` 换成局域网 IP 可让**同一 WiFi 下的真机**连本机服务，
服务端已监听 `0.0.0.0`，无需改代码）。提审前跑一次
`npm run check:build -w @snack/mini -- --release` —— 产物里带着本机地址时它会直接拦下来。

### 持久化模式

| 模式 | 用途 | 状态 |
|---|---|---|
| `DB_MODE=memory`（默认） | 单元测试 / 本机冒烟 / CI，可真实跑完整 HTTP 链路 | ✅ 可用 |
| `DB_MODE=mysql` | 生产：平台库 1 个 + 每租户独立库（D3） | ⏳ S2 随 MySQL 环境接入 |

`DB_MODE=mysql` 目前会**明确报错并列出接入步骤**，而不是静默降级或返回未验证的数据。
理由：本机无 Docker / MySQL，任何 Prisma 实现都无法执行哪怕一次；交付一段从未运行过的
数据库访问层，比明确标记"未交付"更危险 —— 它会让人误以为库存扣减、租户路由这些
最不可返工的部分已经验证过了。

### 四端是怎么来的

一套 uni-app 代码出两个构建目标：

```
apps/mini/src
  ├── build:mp-weixin ──▶ 微信小程序（一个 AppID / 一个包）
  │       ├── 学生端 17 页（主包）
  │       └── 商户端 10 页（分包 /pages-merchant/）
  └── build:h5 ─────────▶ 网页端（同一域名 /admin、/platform）
          ├── 商户网页 11 页
          └── 平台后台 13 页
```

不引第三方 UI 库 —— 否则 AC-04（Token 单一源）、AC-05（语义色零换肤）、AC-06（换肤护栏）
都无法保证。26 个原子组件全部自研。

## 已落地的产品铁律（写进代码，不靠自觉）

这些铁律里有 5 条已经**固化成脚本**（`npm run check:ac`，已并入 `npm run verify`）：
楼栋牌只有一处实现（AC-01）、平台端不碰房间号（AC-13）、学生端没有"确认收货"（AC-15）、
每个状态块都写了"为什么"（AC-16）、停送不清库存（AC-17）。
其余 15 条 AC 是视觉/交互判断，脚本只能验证"引用了正确的 Token"、验证不了"看起来对不对"，
写成子串匹配只会制造假的安全感 —— 它们留在 `docs/AC自查_20条.md` 里人工逐条核对，
每条都写明"看哪里、看什么"。

1. **楼栋只能停用不能删除** —— `DELETE` 直接 403，不是权限问题，是这条路径不该存在
2. **配置缺省即继承店铺** —— 所有读取必须走 `ConfigResolver`，业务代码自行 fallback 会让"加配置项不改表"失效
3. **时间只有一个真相源** —— 能否下单全由服务端判定并下发 `serverTime`，前端只做倒计时
4. **「已截单」用灰不用红** —— 状态→语义色映射集中在 `tokens/index.ts`，业务代码不得自行选色
5. **提交色永不直通** —— 主题色必须过 `guardThemeColor`，算法保证深端白字可读
6. **房间号不出商户库** —— 平台库结构里没有该列；平台侧接口出参过 `assertNoTenantPrivateFields` 断言；日志过脱敏中间件
   （AC-13 已进 `check:ac`：platform 模块里出现 `room` 系列字段访问即失败）
7. **日志必带 tenant_code** —— 由 AsyncLocalStorage 注入，不靠人工传参
8. **样式只能引用 Token** —— `npm run lint:styles -w @snack/mini` 会扫描全库，出现硬编码色值即失败
9. **换肤只改 brand 变量** —— 语义色（ok/warn/danger/info/off）零换肤；平台后台 `lockNeutral()`
   后任何主题色都进不来。**两层**：mini 端是运行时拦 `applyTenantTheme`，网页端是 `.p-shell`
   内 `--brand-*` 就地改写 + `check-platform-neutral.mjs` 源码扫描 —— 只有一层时，
   共用类（`.input:focus` 就引用了品牌色）会成为绕过通道
10. **默认品牌色只存在于 tokens.css** —— 前端 store 不存副本；无租户主题时注入空串，让 Token 生效
11. **组件"被引用"不等于"被注册"** —— uni-app 对模板里用了但没 import 的组件**不报错**，
    只把标签写进 wxml 而不写进 usingComponents，编译全绿、真机才炸。
    `npm run check:build -w @snack/mini` 直接在产物上核对每个 wxml 用到的自定义标签是否都已注册，
    这是 vue-tsc 和 uni 编译器都覆盖不到的死角（已真实踩过一次：A-14 吸底栏）
12. **顶部安全区没有 CSS 解** —— `env(safe-area-inset-top)` 在小程序 webview 里恒为 0，
    且页面样式表在 `app.wxss` 之后加载、同优先级的 `padding` 简写会覆盖掉 class 里的 `padding-top`。
    所以顶部一律走 `composables/useNavMetrics.ts`（实测状态栏高度 + `getMenuButtonBoundingClientRect()`），
    并且**必须写成行内样式**。`base.css` 里故意只有 `.sn-safe-bottom`，没有 `.sn-safe-top`
13. **产物里不得出现本机地址** —— `VITE_API_BASE` 未配置时会静默落到 `http://127.0.0.1:3000`，
    构建全绿、类型全绿，只有真机才炸，而且第一反应会去查域名备案。
    `check:build` 会扫产物并报警，加 `--release` 时直接失败（发布卡口）
14. **受限沙箱里 `vite build` 可能失败在"清空 dist"这一步** —— 这不是代码问题：
    Vite 的 `emptyOutDir` 会批量删除旧产物，触发环境的批量删除护栏（文件数超阈值即拦）。
    绕法是把旧产物**移走**而不是删除（不触发护栏，也不丢东西）：
    `mkdir -p .build-prev && mv apps/web/dist .build-prev/web-$(date +%s)`
    `.build-prev/` 已进 `.gitignore`。正常环境不需要这一步。

## 已知限制

- `DB_MODE=mysql` 未接入（Prisma 仓储层在 S2 补齐；接口契约已由内存实现钉死）
- 平台后台鉴权是单密钥过渡方案，**上线前必须替换为账号体系 + RBAC + 操作审计**
- **商户端小程序的入口依赖平台侧绑定**：店主身份由运营显式绑定
  （`POST /api/platform/merchant/owner`），不由"第一个登录的人"产生 ——
  否则任何先点「我是店家」的学生都会拿到定价权
- **商户网页后台（W-01~W-11）与平台后台（P-01~P-13）已全部落地**，其中两处是过渡实现：
  · **登录是登录码**：网页端不设密码，靠小程序生成的 6 位码换 24 小时店主令牌
    （一次性 · 5 分钟 · 按租户限流 5 次/10 分钟）。它比"网页端直接输密码"强 ——
    把"证明我是店主"交给已验证过的微信身份；但**不是账号体系**，
    上线前必须与 `PLATFORM_ADMIN_KEY` 一起替换为账号密码 / 扫码 + RBAC + 操作审计。
  · **登录码限流是内存计数**：多实例部署时每个实例各计一份，等于放宽 N 倍。
    届时换成 Redis 计数（与推送任务队列一起做）。平台后台的单密钥同理。
- **批量导入只解析 CSV**：解析在浏览器端，入参走真实 `POST /catalog/*`。
  真正的 `.xlsx` 解析要等引入 SheetJS 后替换 `parseCsv()` 一处（后面四步流程一行不用改）
- **数据导出生成的是 CSV**：服务端还没有导出任务接口（长任务队列属 S7/S8），
  现在是浏览器端按当前筛选生成并下载，不占服务端资源也不会过期。订单一次最多取 2000 行
- **S-15 退款申请页按需求未做**：需求 v0.4 把退款定义为**商户功能**（S18），
  学生侧没有退款入口 —— 已支付的单只能由商户发起退款（状态机不变量 ①：
  钱收了就不能直接取消，必须走退款）。学生遇到问题的出路是在订单详情联系店家
- **订阅消息只登记、不发送**：`wx.requestSubscribeMessage` 的授权结果已入库
  （`POST /api/subscriptions`），订单进展也已全量落站内消息；但真正的 `subscribeMessage.send`
  只差公众平台申请的**模板 ID**（AppSecret 已就位），拿到后填进配置即可，**未连线**。
  刻意在这条分支里不消耗一次性授权 —— 否则学生在上线前授权的额度会被"假装发了一次"烧掉。
  模板 ID 就位后只需补 `NoticeService.attemptPush` 的 `senderReady`
- 微信登录链路已就绪，本机已注入 AppID / AppSecret（`apps/server/.env.local`，不入库），
  但**真机尚未验证**：真机要求后端是 https + 已备案域名，IP + 端口在真机上一定不通。
  提审前用 `npm run check:build -w @snack/mini -- --release` 卡一道，防止本机地址被打进包。
  凭据未注入时下单明确报 `WECHAT_NOT_CONFIGURED`，**不会静默降级成匿名下单**
- 支付是**契约级**实现：`POST /orders/:no/pay` 与支付回调的幂等已按 10 次重放验证，
  但微信商户号（mchid / 证书 / APIv3 密钥）未接入，未配置时返回"订单已保留 + 提示"，
  订单仍等倒计时关单 —— **不做假成功**，也不假装已支付
- 依赖交互的状态（输入框聚焦外发光、按钮按压缩放、开关过渡）**在 Playground 里只能说"代码正确"，
  真机手感需在微信开发者工具 + 手机上确认**
- 服务端生产用 `tsc` 编译 + node 运行；dev 用 `node --watch`
  （**不要改用 esbuild/tsx** —— 它们不产出 `emitDecoratorMetadata`，NestJS 构造函数注入会静默失效）
- uni-app 版本固定在 `3.0.0-alpha-5020720260921001`（`vue3` dist-tag），vite 固定 `5.2.8`，
  vue 固定 `3.4.21`，pinia 固定 `2.1.7`。升级前先读 `vite-plugin-uni` 的 `peerDependencies`，
  它把 vite 写成精确版本，放宽会导致构建期静默错配。
