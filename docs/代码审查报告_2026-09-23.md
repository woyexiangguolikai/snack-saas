### 🔴 P0-A　`NODE_ENV=production` 时服务 100% 启动失败（死锁）

**实测**：三种环境变量组合依次启动，两种崩溃，只有一种能起来。

| NODE_ENV | DB_MODE | 结果 |
|---|---|---|
| 不设 | memory（默认） | ✅ 正常启动 |
| `production` | memory | ❌ 抛错 |
| `production` | mysql | ❌ 抛错 |

代码位置：

```ts
// apps/server/src/main.ts:10
if (isProd && env.dbMode === 'memory') {
  throw new Error('生产环境禁止 DB_MODE=memory —— 内存仓储不提供任何持久化保证');
}

// apps/server/src/core/repo.factory.ts:22
throw new Error('DB_MODE=mysql 尚未交付：Prisma 仓储层将在 D2 随 MySQL 环境一起接入。');
```

`memory` 被生产禁止、`mysql` 尚未实现 —— **两条路都堵死**。

**影响**：任何按常规"生产部署"配 `NODE_ENV=production` 的人，服务必然起不来，且堆栈指向两处互相矛盾的原因，很难一眼看明白。

**当前规避**：部署时 `NODE_ENV` 设为 `development`，`DB_MODE=memory`（已写进部署教程）。
**根治**：实现 Prisma 仓储层，或至少让两个约束不要互相打架。

## 二、安全类 P0（公网部署前必须处理）

### P0-1　生产环境 `JWT_SECRET` / `PLATFORM_ADMIN_KEY` 静默回落**公开默认值**

`apps/server/src/core/env.ts:26-31, 50, 60`

```ts
function required(name: string, fallback?: string): string {
  const v = process.env[name];
  if (v && v.length) return v;
  if (fallback !== undefined) return fallback;   // ← 生产也照常回落
  ...
}
jwtSecret: required('JWT_SECRET', 'dev-only-secret-change-me'),
platformAdminKey: required('PLATFORM_ADMIN_KEY', 'dev-platform-key'),
```

这两个默认值写在 `.env.example` 里，**等同公开**。漏配环境变量时服务正常启动、不报错，然后：
- `JWT_SECRET` 用默认值 → 任何人可自行签发 `role:'owner'` 令牌 → 改价、改库存、读全部订单的**房间号与手机号**（AC-13 隐私铁律当场失效）
- `PLATFORM_ADMIN_KEY` 用默认值 → `/api/platform/**` 全线失守

**修复**：`required()` 在生产禁止回落 + 最小长度校验。

### P0-2　`WECHAT_ALLOW_INSECURE_OPENID` 在生产无硬兜底

`apps/server/src/core/env.ts:93-95`

默认值绑了 `NODE_ENV`，但**显式设为 true 时没有任何拦截**。而 `.env.example:28` 里这一项就是 `true` —— 直接把 example 拷成 `.env` 上线就会中招。

打开后：`POST /api/tenant/resolve {appid, openid}` 可用任意 openid 冒名登录；撞到店主 openid 直接拿 owner 令牌。

**修复**：生产环境下显式开启则启动即抛错。

### P0-3　平台后台前端鉴权形同虚设：改一行 localStorage 即可进入

`apps/web/src/stores/platform.ts:31` + `router/index.ts:59`

```ts
export function isPlatformLoggedIn(): boolean {
  return platformSession.key.length > 0;     // 只看长度，不看服务端是否认可

```

控制台执行一行就能进全部 13 个平台页：

```js
localStorage.setItem('snack.platform.key', JSON.stringify({ key: 'x', operator: 'x' }))
```

**修复**：登录后必须有一次服务端背书（`verified` 标志），路由守卫校验 `verified`。

### P0-4　学生令牌可读商户账单与库存矩阵（越权读）

两处守卫缺失：

- `apps/server/src/core/owner.guard.ts:28` —— `GET` 一律放行，学生可 `GET /t/x/api/catalog/matrix?includeOff=1` 拿到全店 SKU×楼栋的可售/预占/已售

## 三、资金类 P0

### P0-5　结算 `settle()` 并发可重复扣费（TOCTOU）

`apps/server/src/ledger/ledger.service.ts:131-186`

幂等判定（`findSettlementRun`）与批次创建之间隔了 3 个 `await`。两个并发调用会双双通过判定，各执行一次 `appendWalletTxn(-feeCents)` —— **余额扣两次**，而 `run.feeCents` 只有一份，对账看板看不出问题。

**修复**：让 `createSettlementRun` 返回 `created`，未创建成功即跳过扣钱；Prisma 实现配 `(runDate, tenantCode)` 唯一索引。

### P0-6　结算批次 `pending` 中间态无人续跑 → 次日二次扣费

`apps/server/src/ledger/ledger.service.ts:131-135`

进程在「扣钱之后、标记之前」重启，批次永留 `pending`。次日 `runDate` 变了 → 这批订单**再扣一次**。

**修复**：命中既有批次时先看 `status`，`pending` 走续跑（只补标记，不重新扣钱）。

### P0-7　同一订单多次退款时，第二次起服务费返还被吞

`apps/server/src/ledger/ledger.service.ts:252`

```ts
const wasSettled = order.status === 'settled';
```

`markOrderRefunded` 会无条件把 status 置为 `refunded`，所以第二次退款时 `wasSettled` 变 false —— 但服务费**已经真扣过了**。商户余额凭空少一笔。

**修复**：改用 `order.settledRunId !== null` 判断"扣过费没有"。

### P0-8　小程序「重新支付」无并发锁 → 可重复发起支付

`apps/mini/src/pages/order/pay-result.vue:192`

`busy` 只在 `invokePay()` 内为 true，而 `start()` 的第一个 `await refresh()` 期间锁是漏的。连点两下会创建两笔预支付。

该页注释自己写着"这一态的存在就是为了防止重复付款"，实际锁没盖住全周期。

## 五、体验类 P2（摘要）

- `SnThumb` 缺 `@load`，`status` 永远卡 `loading` → 图片永不显示
- `useAsync` / `useLoad` 无请求序号保护 → 旧响应覆盖新数据
- `SnStepper` 的 `remove` 事件两处使用方都没接 → 减到 1 后减号是死控件
- `d10()` 取 UTC 日期、`dt()` 取本地时间 → 同一条数据两个控件给出不同日期
- 价格输入框清空后静默变 0 → 学生可 0 元下单
- `snack-saas` 订单 `id` 与订单号序号差 1，人工对单对不上
- `statement_build` 的 `>= 1` 是恒真废条件
