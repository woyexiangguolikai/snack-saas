# 代码审查标准与流程 v1.0

> 适用范围：`snack-saas` 全仓（服务端 NestJS / 小程序 uni-app / Token 包 / 部署脚本）
> 生效日期：2026-09-22　　责任方：技术负责人　　复审周期：每两个月或每次重大事故后

---

## 0. 这份文档要解决什么

**现状**：代码质量参差不齐。同一个坑（比如小程序顶部胶囊区）有人踩过、有人还在踩；
写接口的人不知道前端会因为一个 `127.0.0.1` 白跑一下午。

**根因不是"大家不认真"，而是三件事没做**：

1. **没有分级** —— 改一行文案和改库存扣减走同一套"看一眼就合"，红线改动被当成日常改动放过去了；
2. **清单里混了机器能判的事** —— 格式、色值、组件注册这些交给脚本，人却还在手工核对，于是人和机器都在偷懒；
3. **没有把踩过的坑沉淀成判据** —— 坑只留在当事人的记忆和注释里，换个人就重踩一次。

所以这份文档的组织方式是：

- **能自动化的绝不写进人工清单**（第 5 节的命令是门禁，第 6 节才是人要看的东西）；
- **按"改动性质"分级**，不是按行数（第 3 节）；
- **每条判据都尽量指向一次真实事故**（第 9 节附录 A 是事故账本）。

## 1. 三条基本原则

| # | 原则 | 落地含义 |
|---|---|---|
| 1 | **审查守住"不可返工的部分"，风格交给工具** | 钱、库存、租户隔离、状态机、鉴权、隐私字段 —— 这些改错了要回滚数据甚至赔钱，必须有人看。缩进、命名顺序、引号 —— 交给 lint / 守卫脚本，人不要在这上面花时间。 |
| 2 | **一次审查只对"这次改动"负责** | 审查者发现历史遗留问题，**不阻塞本次合入**，但要登记成独立条目（第 8 节的缺陷账本）。否则没人敢改老代码。 |
| 3 | **作者是质量第一责任人，审查者是兜底** | "审查者没看出来"不是免责理由。作者必须自己跑过门禁命令并把输出贴进 PR（第 5 节）。 |

## 2. 审查对象的边界

**要审**：`apps/`、`packages/`、`scripts/`、`deploy/` 下的源码与配置、`.env.example`、文档中的接口契约。

**不审**（改这些不需要 PR，但仍受门禁约束）：

- `apps/mini/src/styles/tokens.generated.css` —— 生成物，手改会被 `sync-tokens --check` 打回；
- `apps/server/dist/`、`apps/mini/dist/` —— 产物，不入库；
- `apps/server/.env.local`、`apps/mini/.env.local` —— 本机凭据，已 gitignore，**禁止入库**（见红线 R-8）。

---

## 3. 分级：按改动性质，不按改动行数

| 级别 | 触发条件（满足任一） | 审查要求 | 门禁 |
|---|---|---|---|
| **P0 · 红线** | ① 金额 / 账本 / 结算 / 退款；② 库存预占、扣减、回库；③ 租户识别与隔离、`tenantCode` 传递；④ 订单状态机与转移表；⑤ 鉴权、令牌、密钥；⑥ 支付回调与幂等；⑦ 隐私字段（房间号 / 楼层 / 手机号）出参；⑧ 数据迁移与持久化模式 | **双人审查**（其中一人是模块 owner）+ 必须补测试用例 + PR 里必须写**回滚方案** | 全部 + `npm run verify` |
| **P1 · 常规业务** | 新增/修改接口、页面、组件、状态流转的普通改动 | 单人审查 | `npm run verify` |
| **P2 · 轻量** | 纯样式、文案、常量、注释、`.env.example` | 单人快速审查（可只看 diff 摘要） | `npm run verify:mini` 或 `npm run verify:server`（按改动端） |
| **P3 · 紧急** | 线上事故止血，且延迟会造成持续损失 | 可**先合后审**：值班人 + 一人口头确认即可合；**24 小时内必须补正式审查**并回填记录 | 至少 `npm run verify:server` 或最小可验证命令 |

**判定责任**：作者在 PR 标题前打标（`[P0]` / `[P1]` / …）。**标错级别视同缺陷** —— 把 P0 标成 P1 是本次审查中最严重的错误，比代码写错更值得追责，因为它让流程失效。

## 4. 五个审查维度与判据

> 使用方式：审查者按维度逐条过，命中的写进意见。**每条判据都是"能判对错"的**，
> 写不出反例的判据不该出现在这里。

### D1 · 正确性（最贵的一维）

| 编号 | 判据 | 反例 |
|---|---|---|
| D1-1 | **金额一律整数分**，前后端都不出现浮点运算 | `price * 0.9` 做折扣；用 `元` 当参数名却传分 |
| D1-2 | **写操作必须幂等**，且幂等键由调用方生成、随重试复用 | 下单/支付回调/退款不校验 `clientKey`，重试出两单 |
| D1-3 | **并发下的资源竞争有明确归属**：库存预占失败要原样回滚，不得出现负库存 | 先查余量再扣减（查与扣之间被别人插队） |
| D1-4 | **时间只有一个真相源**：能否下单由服务端判定并下发 `serverTime`，前端只做倒计时衰减 | 前端用 `new Date()` 自己算"现在能不能下单" |
| D1-5 | **状态机穷举**：新增状态必须同时更新转移表、可执行动作、语义色、文案四处 | 加了个 `refunding` 状态，但详情页的 `actions` 没给退款动作 |
| D1-6 | **失败路径与成功路径一样被设计过**：网络失败、超时、第三方拒绝、部分成功各有明确归宿 | 只在 happy path 写代码，异常时静默返回空数组 |

### D2 · 数据与租户安全

| 编号 | 判据 | 反例 |
|---|---|---|
| D2-1 | 所有租户数据读写都经 `tenantCode` 作用域，不出现跨租户查询 | 直接用自增 id 查订单，没带租户条件 |
| D2-2 | 平台库结构里**没有**房间号/楼层等租户私有字段；平台侧出参过 `assertNoTenantPrivateFields` | 为了方便排查，把 `room` 加进平台订单列表 |
| D2-3 | 日志过脱敏中间件，且必带 `tenant_code` | 手写 `console.log(order)` 打出完整地址 |
| D2-4 | **密钥只存在于服务端环境变量**，绝不下发到小程序端 | 把 AppSecret 放进 `VITE_*` —— 见 D3-6 |
| D2-5 | 新增接口默认需要鉴权，公开接口要有理由并写进注释 | 新加的 `/api/platform/xxx` 忘了加 `x-platform-key` |

### D3 · 一致性与"唯一真相源"（本项目的核心架构约束）

| 编号 | 判据 | 反例 |
|---|---|---|
| D3-1 | 配置读取必须走 `ConfigResolver`，业务代码不得自行 fallback | 楼栋没配时间窗就 `?? '22:00'` 硬编码 |
| D3-2 | 状态→颜色映射只在 `packages/tokens` 里定义，业务代码不得自己选色 | 页面里写 `status === 'closed' ? '#999' : '#f00'` |
| D3-3 | 金额排版只走 `utils/amount.ts`，全站唯一实现 | 又写一个 `toFixed(2)` |
| D3-4 | 前端**类型照抄服务端出参**，不重新定义业务字段；不解析后端 `message` 文案，只按 `code` 分支 | 前端自己维护一份 `status → 中文` 映射表 |
| D3-5 | 判定不进前端：能不能下单、能不能取消，一律问服务端 `gate` / `actions` | 前端 `if (status === 'pending_pay' && now < expireAt)` |
| D3-6 | **`VITE_*` 变量会被整体内联进客户端产物**，因此其中不得出现任何秘密 | 把 `VITE_WECHAT_APPSECRET` 加进 `.env.local` |

### D4 · 前端交付质量（小程序特有，别处踩不到的坑）

| 编号 | 判据 | 反例 |
|---|---|---|
| D4-1 | 自定义导航页面顶部必须用 `useNavMetrics()` 实测状态栏 + 胶囊几何，且内边距走**行内样式** | 用 `env(safe-area-inset-top)`（小程序恒为 0）；或用 class 写 `padding-top`（被页面样式表的 `padding` 简写覆盖） |
| D4-2 | 右上角胶囊区内不得放任何可点元素（右侧留白 ≥ 实测 `rightReserve`） | 首页把「搜索商品」按钮放在最右侧 |
| D4-3 | 组件**被引用 ≠ 被注册**：模板里用的自定义组件必须 `import`，由 `check:build` 在产物上核对 | 只写了 `<sn-sticky-bar>` 没 import，构建全绿、真机报「组件未找到」 |
| D4-4 | 每个异步区域必须有**三态**：加载（骨架，不留白）、空、错误（给出路） | 请求失败后页面只剩一片空白 |
| D4-5 | 骨架占位尺寸必须与真实内容同高，避免数据到达时跳版 | 骨架 12px、真实文本 18px，内容一加载整体位移 |
| D4-6 | 文案必须中性（`check:copy` 扫描禁用词），错误提示不暴露内部实现 | 直接把后端 `BizError: xxx` 抛给用户看 |
| D4-7 | 样式只引用 Token，不出现硬编码色值（`check-tokens` 强制） | `background: #F26B21` |

### D5 · 可维护性

| 编号 | 判据 | 反例 |
|---|---|---|
| D5-1 | 注释解释**为什么**，不复述代码在做什么；反直觉的选择必须留下原因 | `// 加一` 出现在 `i++` 上方 |
| D5-2 | 没有调试残留：`console.log`、被注释掉的代码块、`TODO` 无负责人 | 提交里带着 `console.log(res.data)` |
| D5-3 | 新增依赖必须说明理由并固定版本；不得引入会改变构建语义的工具 | 把 `tsc` 换成 `esbuild`/`tsx` 跑服务端（丢失 `emitDecoratorMetadata`，NestJS 注入静默失效） |
| D5-4 | 一个 PR 只做一件事。重构与功能改动不得混在同一次提交 | "顺手把整个 store 重写了" |
| D5-5 | 新增的环境变量必须同步更新 `.env.example` 并注明用途 | 代码读 `VITE_FOO`，模板里没有 |

## 5. 门禁：机器先过，人再过

**规则：PR 描述里必须贴出门禁命令的完整输出（不是"跑过了"）。门禁不绿，审查者不开始看代码。**

**CI 会在每个 PR 上自动跑这些命令**（`.github/workflows/verify.yml`）。作者在本机跑是为了早发现，
不是因为 CI 不会跑 —— 但两者都要：本机跑让你在提交前就知道结果，CI 跑保证"通过"这件事不是自述的。

| 命令 | 覆盖什么 | 什么时候跑 |
|---|---|---|
| `npm run verify` | 全量：文案 + 服务端构建 + 冒烟 119 项 + Token 漂移 + 硬编码色值 + 类型 + 小程序构建 + 组件注册 + 本机地址 | P0 / P1 必跑 |
| `npm run verify:server` | `check:copy` → `build:server` → `smoke`（119/119） | 只改服务端 |
| `npm run verify:mini` | Token 漂移 → 硬编码色值 → Token 引用完整性 → `vue-tsc` → `build:mp` → `check:build` | 只改前端 |
| `npm run typecheck` | tokens + server + mini 三包类型 | 都改 |
| `npm run check:build -w @snack/mini -- --release` | **发布卡口**：产物里不得出现 `127.0.0.1` / `localhost` | 每次提审小程序前（CI 的 `release-gate` job 会自动跑） |
| `npm run seed:dev` | 把本机环境铺成"能真跑"的状态（建租户 + 上架商品） | 每次服务端重启后（内存库会清空） |

**CI 的两个 job 为什么分开**（`.github/workflows/verify.yml`）：

- `verify` —— 每个 PR 都跑，**本机地址只警告**（开发分支带 `127.0.0.1` 是合法的）；
- `release-gate` —— 只在合入 main / 打 tag / 手动触发时跑，**本机地址直接失败**。

这不是同一个规则的两种模式，而是两条不同的判据：开发产物的目标是"能连上本机服务"，
发布产物的目标是"能被真机访问"。混成一个 job 就只能二选一，两边都会有人绕过它。

**门禁的定位**：它抓的是**机器能判的错**，占全部缺陷的多数但都是低级的。
门禁全绿只说明"没有低级错误"，**不构成任何质量背书** —— P0 改动仍然必须有人读懂逻辑。

## 6. 流程

```
作者                    门禁                  审查者                 记录
 │
 ├─ 1. 自查（第 4 节清单，按级别取用）
 ├─ 2. 本地跑门禁命令，输出贴进 PR
 ├─ 3. 打级别标 [P0]/[P1]/[P2]/[P3]，填 PR 模板
 │                        │
 │                        ├─ 不绿 → 打回作者（不进入人工审查）
 │                        └─ 绿 ──▶ 4. 按维度逐条审（P0 双人）
 │                                        │
 │                                        ├─ 有 blocker → 作者改 → 回到 2
 │                                        └─ 通过 ──▶ 5. 合入
 │
 └─ 6. 合入后：更新事故账本（若本次修了坑）/ 回填 P3 的补审记录
```

### 各环节的准出条件

| 环节 | 准出条件 | 超时与升级 |
|---|---|---|
| 1–3 作者自查 | PR 模板每一项都有勾选或说明；门禁输出已贴 | —— |
| 4 人工审查 | 所有 blocker 已关闭；should 类意见已回复（改或明确不改 + 理由）；nit 类可挂后续 | **P1 超 1 个工作日、P0 超 4 小时无人响应 → 升级到模块 owner** |
| 5 合入 | 门禁在**合入前的最新基线上**仍是绿的（防止别人的改动把门禁搞红了） | —— |
| 6 事后 | P3 补审 24 小时内完成；事故账本更新 | 逾期 → 下次回顾会通报 |

### 审查意见的分级（作者必须逐条回复）

| 标记 | 含义 | 作者义务 |
|---|---|---|
| `blocker` | 必须改，否则不许合（正确性 / 安全 / 红线） | 改，或给出**能说服审查者的反证** |
| `should` | 应该改，本次不改要留理由和后续条目 | 改，或写明理由 + 建条目 |
| `nit` | 吹毛求疵，可忽略 | 无需回复 |
| `question` | 审查者没看懂，需要解释 | 必须回答（**看不懂通常意味着注释没写够**） |

> 约定：`nit` 不得阻塞合入。把 nit 当 blocker 用，会让作者开始"为了过审而改"，
> 这是审查失效最常见的起点。

## 7. 角色

| 角色 | 职责 | 不做什么 |
|---|---|---|
| **作者** | 分级、自查、跑门禁、写清 PR、逐条回复意见 | 不把"审查者没说"当免责 |
| **审查者** | 按维度审、给可执行的修改建议、判断级别标错 | 不在 nit 上阻塞；不顺手重构别人的 PR |
| **模块 owner** | 该模块 P0 改动的第二审查人；对模块的红线负责 | —— |
| **值班人** | P3 紧急合入的当场确认人；24h 内推动补审 | 不长期替代审查 |
| **守卫脚本** | 第 5 节所有门禁的裁判 | 不替人做判断 |

## 8. 度量与改进

每周记录（数据从 PR 与门禁输出里直接数，不额外填表）：

| 指标 | 含义 | 目标趋势 |
|---|---|---|
| 门禁一次通过率 | 首次提交就全绿的 PR 占比 | 上升 |
| 审查意见中 blocker 占比 | blocker ÷ 全部意见 | 下降（说明作者自查在起作用） |
| 缺陷逃逸数 | 合入后才发现的问题数 | 下降 |
| **缺陷逃逸来源** | 逃逸的问题**该由哪条判据拦住** | 每出现一次逃逸，就补一条判据或一条门禁 |
| 平均审查时长 | 提交 → 通过 | P1 < 1 工作日，P0 < 4 小时 |

**回顾机制**：每两个月或发生线上事故后，做一次 30 分钟复盘，只回答两个问题：

1. 这次事故，**哪条判据本该拦住它**？如果没有，补进第 4 节。
2. 这条判据**能不能变成脚本**？能就变成门禁，从人工清单里删掉。

> 本文档的价值不在于"写得多全"，而在于**每次事故后它都会变长一点**。
> 一个从不更新的审查清单，本质上是一份过期的免责声明。

| 编号 | 红线 | 依据 |
|---|---|---|

| R-2 | 库存不能为负：预占失败必须原样释放 | 零超卖铁律 |
| R-3 | 房间号不出商户库，日志与平台出参必须脱敏 | AC-13 |
| R-4 | 能否下单由服务端判定，前端不得自行判断 | AC-14 |
| R-5 | 状态颜色只能来自 Token，业务代码不得自行选色 | AC-04 / AC-05 |
| R-6 | 样式不得出现硬编码色值 | AC-04 |
| R-7 | 楼栋只能停用不能删除（`DELETE` 一律 403） | 产品铁律 1 |
| R-8 | 密钥、`.env.local`、AppSecret 绝不入库、绝不下发客户端 | D2-4 / D3-6 |

## 10. 附录 A：事故账本（判据的来源）

> 这一节记录**真实发生过的缺陷**及其对应的判据。它是本文件最有价值的部分 ——
> 每条都对应一次实际损失的时间。新增事故时**追加，不要覆盖**。
>
> **入账标准：只有"逃逸"的缺陷才入账** —— 即已经合入、后来才被发现的。
> 被门禁当场拦下的不算事故（那说明门禁在正常工作），不占这里的篇幅，
> 但值得在周会上说一句"哪道门禁今天立功了"，那是判断门禁有没有白写的唯一依据。

| 日期 | 事故 | 影响 | 新增判据 / 门禁 |

## 11. 附录 B：审查者速查（打印版）

**看代码前先问四个问题：**

1. 这次改动**碰到红线了吗**？（第 9 节）→ 碰到就双人审、要回滚方案。
2. 这个值**有几个真相源**？（时间 / 颜色 / 金额 / 配置 / 状态）→ 多于一个就是问题。
3. **失败会怎样**？网络断、超时、第三方拒绝、重复提交 → 有没有明确的归宿。
4. 这个坑**以前踩过吗**？（附录 A）→ 踩过就必须有门禁，不能只靠注释。

**看到这些直接给 blocker：**

- 前端自己算"能不能下单 / 能不能取消"
- 前端自己写 `status → 颜色` 映射
- 金额出现浮点
- 写操作没有幂等键
- `console.log` 打出了地址 / 手机号 / 令牌
- 页面里出现 `#RRGGBB`
- 自定义导航页面用 `env(safe-area-inset-top)` 或 class 写顶部内边距
- `.env.local` 或密钥出现在 diff 里
