# 全链路压测报告 — S8-D

脚本：`scripts/stress.mjs`（`npm run stress -- --concurrency 200`）
日期：2026-09-22 · 环境：`DB_MODE=memory`、`NODE_ENV=development`、本机单实例

---

## 一、为什么单独一个脚本，不塞进 smoke

smoke 回答"**每一条对不对**"，压测回答"**同时来多少还敢说它对**"。

两者的失败含义不同：smoke 红一条就是 bug；压测在 N 并发下红了，要先判断是
"真的有竞态"还是"并发数超过了设计容量"。混在一起会让人在 smoke 全绿时
误以为并发也没问题 —— 而 smoke 里的"连续预占抢 1 件"是**顺序**执行的，
它证明的是"第二次会被拒绝"，不是"同时到达的 50 个里只有 20 个会成功"。

压测走 **HTTP** 而不是直接调服务层：竞态常常出在请求进出的边界
（中间件、上下文、连接复用），直接调服务会把那一层整个跳过，
测出来的是"仓储层没问题"，而用户遇到的是"接口有问题"。

## 二、三个场景与结果

场景设置：压测专用租户、单商品、库存 20 件、并发买 1 件。

### ① 并发抢库存（超卖反证）

| 并发 | 成功 | 失败 | 总耗时 | p50 | p95 | max | 终态（可售 / 预占） | 结论 |
|---|---|---|---|---|---|---|---|---|
| 50 | 20 | 30 | 61ms | 36ms | 50ms | 52ms | 0 / 20 | ✅ |
| 200 | 20 | 180 | 185ms | — | — | — | 0 / 20 | ✅ |

三条判据全部成立：

- **无超卖**：成功数 20 = 库存 20，多出来的请求全部失败
- **库存未为负**：终态可售 0，没有出现 −1
- **守恒**：可售 0 + 预占 20 = 初始 20（一件没多、一件没少）

失败的那 30 / 180 个请求，返回的是业务失败（库存不足），不是 500 ——
这一点同样重要：**并发下的失败必须是"有理由的拒绝"，不能是崩掉**。

### ② 并发重复回调（重复扣减反证）

同一笔订单的支付回调并发重放 25 / 30 次：

- 全部返回成功（幂等重放不是错误，不该报错）
- **全部标记 `idempotent: true`**
- 回调后库存未被扣穿（可售 0 / 预占 19 —— 1 单已确认转已售，符合预期）

重复扣减的典型表现是"库存继续下降直到负数"，这里没有出现。

### ③ 库存流水对账（账实相符）

- 流水 22 条 ≥ 预期 21 条（1 条铺货 + 20 条预占）
- **一条都不缺** —— 流水缺条意味着"账上有、实际没有"，是最难事后补救的一类错误

## 三、结论与边界

```
[stress] 通过 —— 并发 200 下：无超卖、库存未为负、守恒成立、回调幂等、流水完整
```

**必须写清楚的边界**：当前 `DB_MODE=memory`，Node 单线程事件循环会把请求串行化，
所以本结果证明的是"**接口层在高并发下行为正确**"，**不等于数据库层的行锁能力**。

换到真实数据库（MySQL）后，应在相同并发级别下重跑一次：
内存库里"天然串行"掩盖掉的竞态，到 MySQL 上会真实暴露。
那一次的结果才是容量结论的依据。

## 四、复跑

```bash
npm run start:server                        # 另开一个终端
npm run stress                              # 默认 50 并发
npm run stress -- --concurrency 200         # 指定并发
npm run stress -- --appid wxXXX             # 指定 AppID（默认用 .env.local 的）
```

压测会建一家**独立的店**（AppID 后缀 `stress`），不污染演示/开发数据 ——
和演示数据混在一起会让库存基数算不清，守恒判据就没意义了。
