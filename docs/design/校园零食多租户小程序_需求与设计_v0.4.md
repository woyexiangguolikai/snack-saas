# 校园零食多租户小程序 · 需求与设计 v0.4

> 取代 v0.3。本文是**喂给 AI 开发的直接输入**：已定决策、系统模型、场景、功能清单、数据模型、细节约束、实现顺序。

## 0. 前提与边界（已定，作为设计输入）

| 项 | 结论 | 对系统的约束 |
|---|---|---|
| 交付形态 | 每商户独立微信小程序 + 独立微信支付商户号；你方提供统一多租户服务端 | 一套代码 / N 个 AppID / N 个商户号 |
| 资金 | 货款直达商户自己的商户号，你方不碰货款 | 不做分账、不做资金池 |
| 你方收入 | ① **学期订阅费 300 元/学期**（独立账本）② **交易服务费 2%**，从预充值余额扣 | 两个账本、两道独立锁单闸门 |
| 结算 | 预充值。订阅到期或余额归零 → 停止下单 | 「账本 → 租户状态 → 小程序前台」联动 |
| 部署规模 | 目标 50–100 家/月，零个性化 | 必须有租户上线流水线 |
| 市场 | 广西为主 | 学校字典仅作建租户时的楼栋模板来源 |
| 责任 | 你方只提供技术；代办、客服、找客户由合伙人负责 | 系统只处理技术侧数据 |
| **楼栋定位** | **楼栋 = 商户的门店**，是租户级资产，由商户自行维护 | 同校多商户各覆盖不同楼栋，楼栋数据零共享 |
| **库存维度** | **SKU × 楼栋**，楼栋间完全隔离，不可跨楼栋下单配送 | 库存 / 购物车 / 订单 / 配送费全部按楼栋切分 |
| **履约方式** | 商户在宿舍楼内经营，**送达点 = 学生房间内部**，不存在"送至宿舍楼下"的中间态 | 地址精确到楼层与房间号；受宿舍门禁时间约束 |
| **代码推送** | 你方负责推送代码；商户提供上传密钥并自行提审发布 | 必须有版本与发布看板；发版成本随租户数线性增长 |

**一句话概括**：**4 个端 + 1 条上线流水线 + 1 个二维库存矩阵（楼栋 × SKU）+ 1 条宿舍内履约动线。**

## 1. 系统总览

| 端 | 数量 | 归属 | 说明 |
|---|---|---|---|
| 学生端小程序 | 每商户 1 个 | 商户 | 选楼栋 → 浏览 / 下单 / 支付 / 查订单 |
| 商户端 · 小程序内置 | 每商户 1 个（学生端内的商户入口） | 商户 | **配送清单**、接单、改库存、看余额、开关店 |
| 商户端 · 网页后台 | 每租户 1 套 | 商户 | 楼栋维护、批量商品/库存、订单、账单、报表 |
| 平台后台 | 1 套 | 你方 | 租户管理 / 流水线 / 版本发布 / 记账 / 监控 |
| 微信支付 | 每商户 1 个商户号 | 商户 | 只收款，不做分账 |

- **小程序内置端**：**配送清单是它的主页面**（商户人在楼里，边走边操作）、改库存、看余额、开关店
- **网页后台**：楼栋维护、Excel 批量导入、库存矩阵、对账报表、店铺设置
- 两端**共用同一套 API 与权限模型**

## 2. 多租户架构

### 2.1 数据隔离：每租户独立库 + 1 个平台库（D3 已定）

- **平台库**：租户元数据、订阅账本、余额账本、账单、订单汇总、流水线状态、代码版本与发布记录、密钥、监控
- **租户库 ×N**：楼栋、商品、库存矩阵、订单、用户、地址、购物车

**平台库的订单汇总「只存钱，不存人」**：`tenant_code / order_no / amount / fee / status / paid_at / building_code`。

> ⚠️ **房间号绝对不能进平台库、不能进平台侧任何报表、不能落日志**（见 §4.13.4）。它是整个系统里最敏感的数据。

### 2.2 租户识别：单域名 + AppID 换租户（已定）

```
小程序启动
  → wx.getAccountInfoSync().miniProgram.appId
  → POST /api/tenant/resolve { appid }
  → 返回 { tenant_code, config, buildings[], token }
  → 后续请求携带 token，服务端解析租户
```

- 微信小程序 request 合法域名有数量上限，**绝不每租户一个子域名**
- 兜底：路径前缀 `/t/{tenant_code}/api/...`
- 异常：AppID 未匹配租户 → 「店铺未开通」页，不能白屏
- **`buildings[]` 随配置下发** → 商户新增楼栋后学生端立即看到，**无需发版**

### 2.3 配置优先原则（最重要的架构约束）

> **凡是能配置的，绝不要写进代码。**

| 必须配置化（服务端下发） | 只能放代码（发版） |
|---|---|
| 店铺名、logo、主题色、公告 | 页面结构与交互流程 |
| 起送价、配送费、营业时间、**可进入时间窗** | 下单与支付的业务规则 |
| **楼栋清单、排序、启停** | 购物车与订单状态机 |
| 商品、分类、库存 | 组件样式与动效 |
| 每个楼栋的独立配置 | — |
| 首页模块顺序、活动位、提示语 | — |

**推论**：商户日常运营（改价、改库存、加楼栋、调配送费）**100% 不需要发版**。只有"业务规则变了、页面结构变了"才发版，频率应为**每学期 1–3 次**。

### 2.4 代码推送与发版模型

#### 2.4.1 每个新租户要收取的两样凭证

| 凭证 | 在哪里生成 | 用途 | 是否必需 |
|---|---|---|---|
| **代码上传密钥** | 商户后台「开发管理 → 开发设置 → 小程序代码上传」 | `miniprogram-ci` 推送代码的**唯一凭证** | **必需** |
| 项目成员权限 | 商户后台「成员管理」 | 你方登录后台维护配置、上传体验版、看数据 | 建议 |

> ⚠️ **常见误解**：「把你们加为开发者」**不等于**能推送代码。上传密钥只有小程序**管理员**能生成并下载，且可配 IP 白名单（建议只放你方服务器固定出口 IP）。

密钥入库：`tenant_secrets` **加密存储**，平台后台**只可替换不可查看**；失效自动告警。

#### 2.4.2 推送 → 提审 → 发布

```
① 你方：选择版本 → 批量 push 到 N 个 AppID（自动，约 10 分钟）
② 系统：给对应商户发通知「有新版本待发布」
③ 商户：在自己的 mp 后台点「提交审核」
④ 审核通过后，商户：点「发布」
⑤ 系统：记录 released_at，收敛完成
```

**推动权在商户手上** —— 第 ③④ 步客户不动，你只能催。

#### 2.4.3 版本与发布看板（平台后台必备）

每租户一行：`当前代码版本 / 推送时间 / 是否已提审 / 是否已发布 / 推送失败原因`。必须能回答：
- 哪些租户**还停留在旧版本**？
- 哪些租户**已推送但一直不提审**（需催办）？
- 谁推送失败（密钥失效 / IP 未白名单 / 类目变更）？

#### 2.4.4 灰度推送（必须做）

批量推送 = 一个 bug 让 N 个商户同时挂。**先推 1–2 个配合度高的租户 → 验证 → 再批量推剩余**；批量推送要支持"排除名单"。

#### 2.4.5 什么时候迁到开放平台第三方平台

租户数 ≥ 30–50 家 / 一学期发版 > 3 次 / 催审成为固定工作量 → 申请迁移（认证 300 元/年 + 平台审核 + 全网发布 1–2 周）。**不要在 v1 阶段申请**，会与开发期抢时间。

## 3. 两个账本、两道闸门（D1 / D2 已定稿）

### 3.1 为什么不需要微信分账

你方收的是**自己的服务费**，不是代收货款。C 端付给商户的钱全程直达商户自己的商户号。
→ 不归集、不分账、不设资金池，**二清的结构性风险不存在**。

### 3.2 账本一：订阅账本（服务期）

| 项 | 规则 |
|---|---|
| 金额 | 300 元/学期（独立计价，**不并入余额**） |
| 字段 | `period_start / period_end / status / last_renew_at` |
| 提醒 | 到期前 **15 / 7 / 3 天**自动提醒（平台 + 商户后台 + 微信通知） |
| 到期行为 | **停止下单**；前台仍可浏览；文案中性（不写"欠费"） |
| 续费 | 平台后台手动上账（线下转账）为主；线上自助为增强项 |
| 数据保留 | 保留至该学期结束后 60 天 |

### 3.3 账本二：余额账本（2% 交易服务费）

| 项 | 规则 |
|---|---|
| 用途 | 抵扣 2% 交易服务费，与学期无关 |
| 充值 | **100 元起**（线下转账 + 平台后台上账） |
| 计费口径 | 按**订单支付成功**时间挂账；退款成功则**返还**对应服务费 |
| 扣减节奏 | 支付成功写待扣记录 → **每日定时任务汇总扣减** → 生成明细 |
| 预警线 | 余额 ≤ **50 元** → 平台告警 + 商户后台红条 |
| 锁单线 | 余额 ≤ 0 且触及应急额度 → 停止下单 |
| 应急额度 | 允许透支 **20 元**（`credit_limit = -20`） |
| 可追溯 | 每笔扣费能回链到具体订单 |

### 3.4 下单放行条件

```
可下单 = 订阅有效
       AND 余额 > -应急额度
       AND 店铺未手动关店
       AND 当前楼栋处于营业状态（§4.3）
       AND 在营业时间内
       AND 在宿舍可进入时间窗内（§4.13.2）
```

两个账本状态**必须独立显示在平台后台的租户列表上**（订阅剩余天数 / 余额），否则 100 个租户里谁要被停单你看不见。

## 4. 楼栋 = 商户的门店（核心模型）

### 4.1 楼栋是租户级资产，不是学校级字典

| | 说明 |
|---|---|
| 归属 | 楼栋属于**租户**，不属于学校 |
| 同校多商户 | 一所学校 10 栋楼，商户 A 覆盖 1/2/3 栋，商户 B 覆盖 4/5/6 栋，各自独立小程序 |
| 数据关系 | 两商户之间的**楼栋清单、商品、库存、订单，零共享** |
| 重叠 | 同一栋楼理论上可被两个商户同时覆盖，**系统不干预** |
| 学校字典的作用 | **仅**作为建租户时的楼栋模板来源 |

**"楼栋 = 门店"类比的适用范围**：

| 与门店相同的 | 与门店不同的 |
|---|---|
| 库存独立 | 价格全局统一（§4.12） |
| 起送价 / 配送费可独立配 | 营业时间保持租户级（v1） |
| 可单独暂停（某栋今天不送） | 不需要独立客服电话、店招 |
| 订单按楼栋分组配送 | 不需要独立商户号、独立结算 |

### 4.2 楼栋由商户自行维护

**开通向导**：选择学校 → 带出楼栋模板 → 勾选负责的楼栋（可改名、拖拽排序）→ 也可手工新增 → 进入"给商品批量配置库存"。

**日常维护**：新增 / 改名 / 排序 / 停用 / 单独暂停配送 / 调整可进入时间窗。

> **关键**：新增楼栋后**立即生效**，学生端下次打开就能选到 —— 楼栋清单走配置下发（§2.2），**不需要发版**。

### 4.3 楼栋级配置（挂在楼栋上，支持一键配置全部楼栋）

| 配置项 | 楼栋级？ | 说明 |
|---|---|---|
| 起送价 | ✅ | 空 = 继承店铺配置 |
| 配送费 | ✅ | 空 = 继承店铺配置 |
| 营业状态 | ✅ | 可单独暂停某栋配送 |
| **可进入时间窗** | ✅ | 该栋门禁允许的送达时间，默认继承店铺级（§4.13.2） |
| 本栋提示语 / 公告 | ✅ | 例如"1 栋只送到 22:00" |
| 排序 / 启用状态 | ✅ | 后台可调 |
| 营业时间 | ❌（租户级） | 如需按楼栋，用同一机制扩展，**不必改表** |
| 商品价格 | ❌（全局） | 见 §4.12 |
| 客服电话 | ❌（租户级） | — |

**交互要求**：**一键配置全部楼栋**（填一次覆盖所有启用楼栋，常态操作）；只在需要差异时改单个楼栋。
**数据实现**：`buildings.config_override`（JSON），字段缺省 = 继承店铺 —— 将来加新配置项**不用改表**。

### 4.4 商品与库存的楼栋矩阵

**两个"一键同步"操作必须分清：**

| 操作 | 作用 | 场景 |
|---|---|---|
| **同步上架** | 让商品在所有启用楼栋都上架 | 新增一个 SKU 时 |
| **同步库存数值** | 把某楼栋的库存数覆盖到其他楼栋 | 一次性进货，各栋分配 |

**默认行为**：新建商品**默认同步到全部启用楼栋**，需要差异再单独调整；另提供"仅指定楼栋上架"。

**矩阵编辑界面**：商品为行、楼栋为列；单元格编辑、批量勾选、Excel 导入（含楼栋列）。

> **库存的物理含义**：既然履约是"从楼里把货送到学生房间"，`product_stocks` 里 3 栋的库存就是**实际存放在 3 栋、由能进入 3 栋的人送出的那批货**。所以"库存按楼栋独立"不是功能设计，是**物理事实的映射**；分栋备货是常态，跨栋调货是例外（用调拨记录）。

### 4.5 楼栋的三层一致性（最易出错的地方）

| 层 | 含义 | 规则 |
|---|---|---|
| 浏览上下文 | 学生当前所在楼栋（顶部可切换） | 商品列表、库存、售罄状态、起送价、配送费全部按此楼栋渲染 |
| 购物车 | **购物车带 `building_id`** | 一个购物车只能属于一栋楼；**切换楼栋自动清空购物车**（D8，加轻提示，不弹确认框） |
| 订单 | **订单带 `building_id`** | 服务端校验：订单楼栋 == 购物车楼栋，且每个 SKU 在该楼栋库存充足 |

**地址簿里的「楼栋」不决定订单楼栋，只用于校验。** 不一致时拦截：「当前购物车商品属于 1 栋，无法配送到 2 栋」。

理由：商品在哪个楼栋卖，是**商家的库存**决定的，不是学生的地址决定的。

**订单提交后楼栋与房间号不可修改**（库存已按该楼栋预占），要改只能取消重下。

### 4.6 商品在楼栋间的三种状态（必须区分）

| 状态 | 数据表现 | 前台表现 |
|---|---|---|
| 未在该楼栋上架 | 无 `product_stocks` 记录或 `status = 下架` | **不显示**（不是显示"售罄"） |
| 在该楼栋上架但库存 0 | `stock = 0` | **显示售罄**，不可加购 |
| 正常在售 | `stock > 0` | 可加购 |

### 4.7 库存并发与预占

`product_stocks` 三个数量列：`stock`（可售）/ `locked`（已下单未支付，预占）/ `sold`（已支付累计）。

| 时点 | 操作 | SQL 语义 |
|---|---|---|
| 下单 | 预占 | `UPDATE ... SET stock=stock-N, locked=locked+N WHERE product_id=? AND building_id=? AND stock>=N`，**影响行数 = 0 即拒绝**（防超卖） |
| 支付成功 | 转已售 | `locked-N, sold+N` |
| 超时 / 取消 | 释放 | `locked-N, stock+N` |
| 退款成功（未送达） | 回库 | `sold-N, stock+N`（已送达的退款不回库，由商户决定） |

一条 UPDATE 完成原子预占，不需要分布式锁。变动写 `stock_logs`（下单 / 支付确认 / 取消释放 / 退款 / 人工调整 / 调拨）。

### 4.8 楼栋生命周期：只能停用，不能删除

被历史订单 / 库存流水引用后，删除会导致订单、流水、报表全部对不上。停用后：前台不可选、新订单不可用；**历史订单不受影响**。

### 4.9 单楼栋商户自动降级

- 建租户时自动创建「默认楼栋」
- **有效楼栋数 = 1** 时：前台隐藏楼栋选择器、后台隐藏楼栋列、批量操作自动选中该楼栋
- 商户完全感知不到这套模型存在

### 4.10 楼栋变更场景（"楼栋 = 门店"的核心价值）

| 场景 | 操作 | 系统行为 |
|---|---|---|
| **接手新楼栋** | 后台新增楼栋 → 给商品设库存 | **立即生效，无需发版**；该栋学生马上下单 |
| **退出某栋** | 停用楼栋 | 前台不可选；历史订单与流水完整保留 |
| **某栋临时不送** | 楼栋级暂停配送 | 该栋显示"今日已停送"，其他栋正常 |
| **楼栋改名** | 直接改 | 前台立即更新 |

### 4.11 学生端边界（必须处理）

1. **学生所在楼栋不在该商户覆盖范围** → 只显示商户已启用的楼栋 + 引导语「没有找到你的楼栋？本店暂未覆盖」
2. **切换楼栋后购物车被清空** → 轻提示「已切换到 2 栋，购物车已清空」
3. **已选楼栋被商户停用**（学生停留在旧页面） → 下次请求返回"该楼栋已停送"，引导重新选择
4. **上次选择的楼栋记住**：本地缓存 + 服务端记录，下次进入直接进入该栋

### 4.12 明确的设计判断：价格全局统一，不按楼栋

**不做楼栋级价格。** 收益极低（同校同商户的零食，学生互相通气，按栋定价只会招投诉）；成本极高（下单要按栋取价、改价要按栋改、"一键同步"语义被打乱、对账报表全要按栋拆）。

**价格差异只能由"不同商户"产生，不能由"同一商户的不同楼栋"产生。**
将来若确有需要，用 `config_override` 扩展即可，**不必改表**。

### 4.13 履约：送达点是学生房间

#### 4.13.1 地址精度

| 字段 | 必填 | 说明 |
|---|---|---|
| 楼栋 | ✅ | 决定库存与可下单性 |
| **楼层** | 建议 | 用于配送排序与动线规划；可填可不填，不填则按房间号排序 |
| **房间号** | ✅ | 文本，兼容 302 / 3-302 / A302 等格式，不做强校验（各校格式不一） |
| 联系电话 | ❌ | v1 不强制（见 §9）；留"送到房间"的备选联系方式 |

**地址簿的实际情况**：学生自己房间是固定的 → 首次填写后记为默认地址；支持**送到他人房间**（给同学带），所以地址簿保留多地址能力，但常态只有一个。

#### 4.13.2 可进入时间窗（门禁约束）

宿舍有门禁 / 熄灯时间，所以"营业到 23:30"在系统上是假配置——单能下、送不进去。

**设计**：
- 配置 **"楼栋可进入时间窗"**（租户级默认，楼栋级可覆盖，例如 06:30–22:30）
- 商户的营业时间**必须落在窗口内**，超出部分系统截断
- 还要预留配送在途时间 → 真正的**截单时间早于窗口结束**（如窗口 22:30，截单 22:00）
- 超出时间窗：前台不允许下单，展示"今日已截单"与下次可下单时间

> 这种"下了单送不到"的订单，一条就够学生在群里骂一晚。

#### 4.13.3 商家端核心视图：配送清单

商户人在楼里，一趟要把同栋的货全送完。所以**按时间排序的订单列表对他没用**，他要的是：

```
配送清单（按楼栋分组）
├─ 2 栋 ── 待送 5 单
│   ├─ 6 楼 602  订单 #A...  （2 件）
│   ├─ 6 楼 615  订单 #B...  （1 件）
│   ├─ 3 楼 308  订单 #C...  （3 件）
│   └─ ...
└─ 3 栋 ── 待送 2 单
    └─ ...
```

- 排序：楼栋 → 楼层（倒序或正序）→ 房间号
- 操作：**逐单勾选送达** + **批量标记送达**（一趟送完一键清）
- 同一订单可能跨多栋？**不可能**——订单与购物车都绑楼栋（§4.5），一个订单只属于一栋
- 送达后：订单状态 → 已送达，并触发订阅消息通知学生

#### 4.13.4 送达确认与房间号隐私

| 项 | 设计 |
|---|---|
| 完成触发 | **商户标记"已送达"** 即完成，不做学生确认收货（学生不会点，会让订单永远挂着） |
| 兜底 | 送达后 N 小时未操作则自动完成（§9） |
| 学生侧 | 收到订阅消息「订单已送达」 |
| 争议 | 系统记录送达时间；送达凭证（备注/拍照）为增强项（B4） |

**房间号隐私（硬要求）**：

1. **平台库不存房间号** —— 平台侧只有 `building_code`
2. **平台侧任何报表、导出、日志都不出现房间号**
3. **你方运营账号在后台看不到房间级信息**，只能看到楼栋级
4. 房间号只对**接单的商户**可见；未来多店员时按角色限权
5. 学生端隐私政策需披露：房间号将提供给商户用于配送
6. 这条同时是"你方只提供技术"最实在的一道墙：**房间里发生的纠纷，你手上不该有**

## 5. 租户上线流水线

| # | 阶段 | 负责方 | 自动化 |
|---|---|---|---|
| 1 | 资料收集（执照、法人身份证、店铺名、logo） | 合伙人 | 表单 + 上传 |
| 2 | 办执照 / 食品备案 | 合伙人（线下） | 只记录状态与证件有效期 |
| 3 | 小程序注册 + 微信认证（300 元/年） | 商户 | 商户本人 |
| 4 | 小程序 ICP 备案 | 商户 / 合伙人 | 各省 1–20 个工作日，不可控 |
| 5 | 微信支付商户号申请 + 绑定 AppID | 商户 | 需人脸 / 打款验证，**你代不了** |
| 6 | 服务类目申请（食品） | 商户 | 需资质材料 |
| 7 | **取得代码上传密钥 + IP 白名单 + 项目成员权限** | 商户（你方指引） | 见 §2.4.1 |
| 8 | 平台侧创建租户（建库、初始化、**带出学校楼栋模板**） | 系统 | 一键 |
| 9 | **推送代码**（灰度：先 1–2 家，再批量） | 系统 | 自动化 |
| 10 | **商户提审 + 发布** | 商户 | ❌ 人工，推动权在商户 |
| 11 | 商户充值 → 开通 | 系统 | 自动 |
| 12 | 商户维护楼栋 + 配置商品库存 + **设置可进入时间窗** → 营业 | 商户 | 自助，**无需发版** |

### 三个非代码瓶颈

1. **审核会驳回** → 状态机必须有 `驳回` 状态 + `驳回原因` + **返工队列**
2. **商户号必须本人办理** → 每个租户记录**卡在哪一步、卡了几天**，这是平台后台最重要的看板
3. **密钥与版本运维** → 密钥加密、只可替换不可查看；版本与发布看板见 §2.4.3

### 六条建模铁律

1. **金额一律用整数「分」**，不用 float / decimal 参与计算

6. **房间号只存在于租户库**，任何情况下不落平台库、不进平台报表、不落日志

## 9. 魔鬼细节清单

### 楼栋与库存

1. **楼栋绑定层级**：浏览上下文 → 购物车 → 订单，三层一致，以购物车为准（§4.5）
2. **未上架 ≠ 售罄**：某楼栋不卖的商品**不显示**（§4.6）
3. **切换楼栋自动清空购物车**（已定），要给轻提示，不能静默清空
4. **服务端必须二次校验楼栋**，防止客户端篡改 `building_id` 绕过库存
5. **单楼栋自动降级**：楼栋数为 1 时隐藏全部楼栋 UI（§4.9）
6. **楼栋停用不影响历史订单**
7. **没有"同步到全部楼栋"，商户要做 3 栋 × 50 SKU = 150 次手工输入** —— 批量能力是体验命门
8. **"同步上架"与"同步库存数值"是两个操作**，界面必须分开（§4.4）
9. **楼栋新增后立即生效**（走配置下发），这是"楼栋 = 门店"能成立的前提
10. **价格不按楼栋**（§4.12），避免改价与对账被楼栋维度污染

### 履约与送达

11. **送达点是学生房间内部**，不存在"送至宿舍楼下"的中间态
12. **截单时间必须早于可进入时间窗结束**，预留配送在途时间（§4.13.2）
13. **商家端主视图是配送清单，不是订单列表**：按楼栋分组、按楼层排序、支持批量送达（§4.13.3）
14. **一个订单不可能跨楼栋**（订单与购物车都绑楼栋），配送清单天然按栋分
15. **完成触发是"商户标记送达"**，不做学生确认收货；另设送达后 N 小时自动完成兜底
16. **楼层为可选字段**，不填则按房间号文本排序；房间号格式不做强校验（各校格式不一）
17. **房间号隐私硬要求**：不进平台库、不进平台报表、不落日志、你方运营账号看不到（§4.13.4）
18. **订单提交后楼栋与房间号不可改**，要改只能取消重下（库存已按栋预占）

### 发版与推送

19. **"加为开发者" ≠ 能推送代码** —— 必须要「代码上传密钥」（§2.4.1）
20. **一次发版 = N 次商户手动提审发布**，推动权在商户手上 → 坚持"能配置的绝不发版"（§2.3）
21. **批量推送必须支持灰度**（先 1–2 家，再批量），一个 bug 会让 N 个租户同时挂
22. **商户可能自行改代码或委托第三方改** → 与你方推送冲突；协议中需约定"代码以我方版本为准"
23. **上传密钥可能被商户重置** → 失效告警 + 一键重新收集流程
24. **ci 推送受 IP 白名单限制** → 你方服务器需固定出口 IP

### 通用

25. **request 合法域名有上限** → 单域名 + AppID 识别，绝不每租户一个子域名
26. **微信订阅消息一次授权只能发一条** → 发给最关键的状态变更
27. **获取手机号需用户主动授权且可能计费** → v1 不强制手机号，用「楼栋 + 房间号」完成履约
28. **小程序 ICP 备案**是上线周期里最大的不确定项，主体是商户
29. **支付回调必须幂等** → `order_no + 状态机` 去重
30. **「支付成功但订单未生成」** → 对账任务扫支付流水 vs 订单表，差异自动补单
31. **超时未支付自动关单** + **送达后 N 小时自动完成**，否则订单永远挂着，账单算不准
32. **余额扣减可追溯**：每笔扣费能回链到具体订单
33. **锁单不能是硬开关**：提前预警 + 应急额度 + 中性文案
34. **日志带 tenant_code**，否则 100 个租户的日志混在一起
35. **租户库可独立备份恢复**：商户误删商品或跑路，你要能救
36. **校园强季节性**：寒暑假订单归零，资源可降配；到期日要避开假期
37. **上线前预置演示商品与楼栋**，否则空壳小程序审核大概率驳回

## 11. 实现顺序（按技术依赖排，不是按界面排）

1. **多租户底座**：租户识别、租户库建库与迁移、**配置下发（含楼栋清单与时间窗）**
2. **楼栋模型**：楼栋表 + `config_override` + 商品 × 楼栋库存矩阵 + 库存流水
   （数据模型一旦定型，后期改动代价最大，必须最先做对）
3. **双账本 + 两道闸门**（你唯一的收钱通道）
4. **商品 + 楼栋选择 + 购物车 + 下单 + 支付闭环**（单租户跑通，含时间窗校验）
5. **订单状态机 + 库存预占释放 + 通知 + 退款**
6. **商户端网页后台**：楼栋维护、商品、库存矩阵、订单、Excel 导入、时间窗配置
7. **商户端小程序内置版**：**配送清单**（复用第 4–6 步 API）
8. **平台后台：租户管理 + 上线流水线 + 代码推送与版本看板**
9. **账单 / 对账 / 监控 / 到期提醒任务**
10. **B4 增强项**

> 顺序的理由：**先把「能收钱」和「能上线一个新租户」两条链路打通**；界面漂不漂亮是最后的事。
