# 校园零食多租户小程序 · 开发计划与里程碑 v1.0

> **本文档定位**：把《需求与设计 v0.4》的 11 步实现顺序 + 《全量页面与闭环 v3.0》的 51 页 / 42 闭环 / 20 条 AC，翻译成**可执行、可验收、带日期**的作战计划。
> **交付形态**：4 端代码 + 上线流水线 + 二维库存矩阵 + 宿舍内履约动线。
> **执行模式**：AI 写全部代码、跑全部验证；人只做决策与验收。
> **工期**：7 天（D1–D7）交付 v1.0 代码；D8–D10 灰度试运营；真实上线日由外部依赖决定。

### 0.3 一周硬约束下的范围裁定（关键判断）

v0.4 的 D6 明确「不切分，做全量」。本计划**不砍功能**，但把交付物按「能否由 AI 独立完成」切成三层：

```
┌─ P0 · AI 可独立交付（D1–D7，必交） ──────────────────────────┐
│ 4 端全部 51 页 + 42 条闭环 + 双账本 + 库存矩阵 + 上线流水线    │
│ + 20 条 AC 自查通过 + 演示种子数据 + Docker 一键部署            │
└──────────────────────────────────────────────────────────┘
┌─ P1 · AI 可交付（D8–D10，增强项） ───────────────────────────┐
│ B4：按楼栋经营看板 / 数据导出 / 送达凭证 / 自助续费 / 多店员   │
└──────────────────────────────────────────────────────────┘
┌─ 外部依赖 · AI 无法完成（决定真实上线日） ────────────────────┐
│ 小程序注册 + 微信认证（300/年）｜ICP 备案（1–20 工作日）        │
│ 微信支付商户号（人脸/打款）｜代码上传密钥 + IP 白名单           │
│ 食品服务类目资质｜商户提审与发布｜微信审核                        │
└──────────────────────────────────────────────────────────┘
```

> ⚠️ **必须先说清的一句话**：**代码一周内可以写完，但「真实上线」一周内不可能完成。**
> 卡点不是代码，是 ICP 备案（1–20 个工作日，主体是商户）与商户号本人办理。
> 因此本计划把「代码交付日」（D7）与「上线日」**解耦**：D7 交付的是「接上商户凭证即可推送」的完整系统，D8–D10 用体验版 + Mock 支付在真实小程序环境全链路验证。

### 0.4 一句话结论

**D7 交付可直接上线运营的 v1.0 代码（4 端 51 页全通、42 闭环全通、20 条 AC 全过）；真实首个租户上线时间由商户的 ICP 备案与商户号办理进度决定，与开发进度无关。**

## 1. 技术方案锁定

### 1.1 一套代码，四个端

```
                    uni-app (Vue3 + Vite + TS) 单一代码库
                    ├── build:mp-weixin ──▶ 微信小程序（一个 AppID / 一个包）
                    │      ├── 学生端 17 页（主包）
                    │      └── 商户端 10 页（分包 /pages-merchant/）
                    └── build:h5 ─────────▶ 网页端（同一域名 /admin、/platform）
                           ├── 商户网页 11 页（W-01 ~ W-11）
                           └── 平台后台 13 页（P-01 ~ P-13）
```

**为什么商户端小程序放在同一包里**：v0.4 §1 明确「商户端·小程序内置 = 学生端内的商户入口」，两端**共用同一套 API 与权限模型**。同一包内以分包隔离，登录态靠角色判定分流。

**为什么网页端也走 uni-app H5**：Token 与 36 类组件单点复用是 AC-04（Token 单一真相源）的前置条件。网页端另加一层桌面布局适配（`min-width:1024px` 下切「筛选栏 + 表格 + 分页」结构）。

### 1.2 技术栈清单

| 层 | 选型 | 理由 |
|---|---|---|
| 小程序 / H5 | uni-app 3.x + Vue3 + Vite + TypeScript + Pinia | 一套代码多端；Vue3 组合式 API 便于把设计系统做成 hooks |
| UI 基座 | **自研组件库**（直接复刻 v3.0 设计系统 36 类组件 + Token） | 不引第三方 UI 库，才能保证 AC-04 / AC-05 / AC-06 |
| 后端 | NestJS 10 + TypeScript | 模块化清晰、装饰器式多租户拦截器与守卫 |
| ORM | Prisma 5（平台库 + 租户库动态连接） | 迁移脚本可编程，租户建库走同一套 migrate |
| 数据库 | MySQL 8（**每租户独立库 + 1 平台库**，D3） | 对齐 v0.4 §2.1；租户库可独立备份恢复（细节 35） |
| 缓存 / 队列 | Redis 7 + BullMQ | 幂等键、库存去抖、定时任务（关单 / 日扣费 / 送达自动完成 / 到期提醒） |
| 支付 | 微信支付 V3 JSAPI（`wechatpay-node-v3`），抽象为 `PayProvider` | 沙箱期可切 Mock，D8 无缝换真实 |
| 推送 | `miniprogram-ci`，抽象为 `DeployProvider` | v0.4 §2.4 的 D4；30–50 家后迁第三方平台 |
| 部署 | Docker Compose（mysql / redis / api / worker / web / nginx） | 50–100 家/月规模下单机足够；租户库隔离不靠物理机 |
| 监控 | 自建 `audit_logs` + 结构化日志（**必带 tenant_code**，细节 34）+ 告警任务 | 平台后台 P-10 监控告警页的数据源 |

### 1.3 多租户落地方案（D1 就必须定型，后期改动代价最大）

| 议题 | 方案 | 依据 |
|---|---|---|
| 租户识别 | 小程序启动 → `wx.getAccountInfoSync()` → `POST /api/tenant/resolve {appid}` → 返回 `{tenant_code, config, buildings[], token}` | §2.2 |
| 域名 | **单域名 + 路径前缀** `/t/{tenant_code}/api/...`，绝不每租户一个子域名 | §2.2 细节 25 |
| 数据隔离 | 平台库 1 个 + 租户库 N 个；`TenantRouter` 按 token 里的 tenant_code 取连接 | §2.1 D3 |
| 配置下发 | `GET /t/{t}/api/config` 返回店铺配置 + **楼栋清单 + 时间窗**，楼栋新增**立即生效不发版** | §2.3 §4.2 |
| 平台库订单汇总 | **只存钱不存人**：`tenant_code/order_no/amount/fee/status/paid_at/building_code` | §2.1 |
| 房间号 | **只存在于租户库**；数据访问层不返回、不进平台报表、不落日志 | §4.13.4 D16 AC-13 |
| 密钥 | `tenant_secrets` 加密存储，平台后台**只可替换不可查看**，失效自动告警 | §2.4.1 |

**六个关键抽象（先定接口，后填实现）**

| 抽象 | 职责 | 为什么必须先做 |
|---|---|---|
| `TenantRouter` | AppID / tenant_code → 租户库连接 + 配置 | 所有请求的入口 |
| `ConfigResolver` | 楼栋级 `config_override` 与店铺级配置的合并（**缺省即继承**） | 决定「加配置项不改表」（铁律 5） |
| `StockGate` | 单条原子 UPDATE 预占 / 释放，影响行数 = 0 即拒绝 | 防超卖（§4.7） |
| `OrderStateMachine` | 订单状态唯一的合法迁移表 | 支付回调幂等（细节 29） |
| `PayProvider` | 统一下单 / 回调验签 / 退款 | 让沙箱期与真实期可切换 |
| `DeployProvider` | 版本 → N 个 AppID 的灰度批量推送 | 上线流水线的核心（§2.4.4） |

### 1.4 部署拓扑

```
             Nginx（单域名 + HTTPS）
                │
    ┌───────────┴────────────┐
 /t/{tenant}/api          /api（平台）
    │                        │
    └──────► NestJS API ◄─────┘
                │
    ┌───────────┼────────────┬──────────────┐
 MySQL 平台库  MySQL 租户库×N   Redis        BullMQ Worker
                │                          （5 类定时任务）
                └─ /data/tenants/{code}/   每日备份，可单库恢复
```

## 3. 职责划分（RACI）

| 角色 | 说明 | 本期投入 |

| **AI 开发执行体** | 本助手（含子代理）：全部编码、迁移、种子数据、测试、自查、部署脚本、文档 | 全时 |

#### S2 交付记录（收口时补记）

S2 实际交付**两半**：**钱**（`src/ledger/`）与**货**（`src/catalog/`）。
原计划只写了钱，但 V2 验收里含「库存矩阵 API」与 AC-10/AC-11/AC-12，
而库存正确性（不超卖）与账本正确性（分毫不差）是同一类问题 —— 都需要"一条原语保证原子性"，
所以一并做了。

| 半 | 内容 |
|---|---|
| **钱** | 双账本 · 每日汇总扣减任务（可注入 now 跨日验证）· 退款返还 · 到期 15/7/3 提醒 · 中性文案模块 |
| **货** | 商品三态（未上架 ≠ 售罄 ≠ 在售）· 零超卖 · 七类库存流水 · 两个同步语义（AC-10）· 双重编码（AC-11）· 跨栋调拨 |

**关键设计决定：库存变更收敛为两个仓储原语**

初版把 `reserveStock` / `transferStock` 写进仓储接口 —— 问题有两个：
每加一个业务动作就要加一个仓储方法；且"超卖不超卖"这个正确性属性被摊到多个方法里，
将来写 Prisma 版要逐个方法保证原子性，迟早漏一个。

收敛后业务层再没有"先查再改"：

- `moveStock` —— 无条件增量，对应 `SET stock = stock + ?`
- `moveStockIf` —— 条件迁移，对应 `... WHERE status='on' AND stock + ? >= 0`

七种迁移（`order_hold` / `pay_confirm` / `cancel_release` / `refund_return` /
`manual_adjust` / `transfer_out` / `transfer_in`）全部由这两个原语组合出来。
**真库只需保证"一条 SQL 一条语句"，正确性只在一个地方需要证明。**

**"库存对得上"的可执行定义**：`stock === Σ 该格全部流水的 change`。
注意 `locked` / `sold` 不参与求和 —— 预占是 stock−− 与 locked++ 同时发生，
而流水只记 stock 侧，把它们加进来反而会错。
